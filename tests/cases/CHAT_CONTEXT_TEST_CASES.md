# Retrieval-first Chat Context Test Cases

Status: as of 3.2.42, the original regressions and CTX-M01–M18 have executable
coverage; the placeholder mechanism TODOs have been replaced. Bounded offline
tests cover deterministic refinement, measured context boundaries and evidence
recovery. Runtime/encoder and installed-host gates are separate from that core
suite. This does not close VAL-02/03: live-model long-task quality, semantic
compression quality, resource thresholds and broader platform/multi-component
acceptance still require their own evidence.

## Running and interpreting the baseline

```sh
npm run test:chat-context
```

The command builds the extension and runs the core context suite, including
[test-chat-context-contracts.js](../test-chat-context-contracts.js). Its regression
assertions cover the production implementation. Do not invert them,
catch their assertion failures, disable History, or mark them TODO to obtain a
green suite. The executable context gate also runs during packaging.
Use `npm run test:chat-context:acceptance` for the broader gate, including the
runtime/encoder and installed-host checks; an offline core run does not execute
or revalidate those environment-dependent checks.

Fixtures are generated by [chat-context.js](../fixtures/chat-context.js). They
contain no captured private chat, query, document, credential or model response.
The large fixture has 17 tool calls with one exact relevant result and enough
irrelevant content to exceed 100,000 historical request characters.

- `CTX-U`: executable unit/boundary/preservation tests.
- `CTX-R`: executable desired-behavior regressions; all eight now pass.
- `CTX-T`: executable controller + real disk + loopback HTTP transport tests.
- `CTX-M`: executable mechanism assertions mapped to M01–M18 below; coverage is
  split across core, runtime/encoder and installed-host tests, not all provided
  by the offline transport fixture.

`CTX-T`/transport regressions stub the VS Code host, selected model configuration
and retrieval adapter. They do not stub the controller, persistence, OpenAI
client, budget checks or HTTP response parser. They are not full Extension Host
or real retrieval-worker E2E. The HTTP server returns a synthetic answer;
correct evidence selection is asserted against the transmitted payload, never
inferred from that answer.

The `CTX-M11/M13/M17` eviction/retry regression composes three otherwise separate
boundaries: a real loopback request must exceed the measured planner budget,
evict an older complete tool group, and fail before an explicit retry. A reopened
disk store then supplies a hash-checked exact range through `session_info`; the
next transmitted request and persisted manifests must contain that range.
It asserts unchanged prior attempts, no mutation replay, and exactly five
synthetic provider requests (three before failure, two during recovery).
Diagnostics report the measured before/budget/after counts and recovered length.
This exercises deterministic selection and recovery, not semantic compression,
live-model task quality, process-crash recovery, or installed Host acceptance.
For offline runs against existing compiled artifacts without rebuilding:

```sh
mkdir -p .ctx-offline-fixtures
TMPDIR="$PWD/.ctx-offline-fixtures" node --test tests/test-chat-context-contracts.js tests/test-chat-context-mechanisms.js tests/test-chat-evidence-reader.js
rmdir .ctx-offline-fixtures
```

## Required mechanism observability

Each production attempt must expose bounded events sufficient to verify:

| Event | Required observations |
|---|---|
| Retrieval | attempt ID, query reference, scope, actual serving identity/version, candidate references |
| Selection | selected immutable chunk IDs/ranges, excluded reasons, evidence-condition relationships |
| Budget check | input count, counting method, schema/image overhead, reserved output, available limit |
| Refinement | parent reference, reason, splitter/projection version, children, before/after cost |
| Re-retrieval | prior attempt, changed query/scope/granularity, novel evidence |
| Compression | method, source references, reason, before/after cost; distinct from refinement |
| Stop | budget-fit/no-progress/limit/cancel/unavailable reason, unresolved needs |
| Send | round ID and actual final selection manifest matching provider payload |
| Feedback | episode/attempt, signal source/confidence, eligibility and model identity |

These are observation contracts, not a list of literal implementation event names.
Mechanism tests must assert positive and negative activation, call counts,
ordering, reasons and bounds. Do not infer activation only from a short prompt
or from the absence of a 100K error. Use an injected clock and counting adapter
for deterministic boundaries; separately test production counting adapters.

## Activation and stopping matrix

Let `B` be available input after mandatory instructions, current input, tool
schemas, image costs, output reservation and the declared safety margin.
Measure after retrieval and initial selection, not against the entire stored
corpus. Do not hard-code model-independent token or compression thresholds.

| ID | Scenario | Must start | Must not start / stopping oracle |
|---|---|---|---|
| M01 | Selected subset costs `B-1` or `B` | Initial retrieval/selection | No refinement, re-retrieval, compression or LLM rewrite |
| M02 | Selected subset costs `B+1` | Budget-driven refinement after initial selection | No pre-retrieval compression; no premature model send |
| M03 | First refinement yields sufficient evidence within `B` | One refinement/reselection | No additional attempt or shortening; one answer request |
| M04 | Retry returns only previous evidence | No-progress detection | No unbounded identical retries or success-shaped fallback |
| M05 | Attempt, elapsed-time, candidate or resource boundary reached | Explicit bounded stop | No operation beyond limit; unresolved needs remain visible |
| M06 | One large mixed-topic JSON/table contains the answer | Structure-aware children and condition completion | No malformed JSON presented as complete; no metric detached from test conditions |
| M07 | Long unknown prose remains large | Boundary splitting and extractive selection | No heuristic deletion of negation, clauses or units |
| M08 | Deterministic strategies exhausted; LLM fallback not approved | Explicit unresolved/failure state | Zero LLM shortening calls and zero implicit model downloads |
| M09 | Source changed between retrieve and materialize | Revision rejection/invalidation | No stale chunk injection or old feedback identity reuse |
| M10 | Same input/source/splitter version processed twice | Stable child IDs and ranges | No duplicate child publication; changed version must be distinguishable |
| M11 | Tool results grow over several rounds | Budget planning before every model round | No orphan tool results, tool replay, permission expansion or false success |
| M12 | Steering arrives while tool round runs | Plan with steering before dequeue | Failed plan retains input; successful plan consumes it once |
| M13 | Retry or approved delegation | Same planner with target's scope/model | No sender-history leak, draft-image leak or replay of prior side effects |
| M14 | Selection changes after refinement | Final request receipt | No pre-refinement selected flags/counts reported as transmitted |
| M15 | Learned solution falls back to BM25 | Record actual served path and fallback | No attribution to the requested but unused model |
| M16 | Feedback opt-in off or revoked | Normal request execution | No training data capture, raw-text telemetry, sync/upload or serving update |
| M17 | Crash between blob/index/manifest publication | Recovery or explicit missing-source failure | No dangling reference accepted as valid evidence |
| M18 | Real installed Extension Host and browser | UI, planner, store and selected provider path | Do not count a controller stub as host E2E |

The M IDs map to executable assertions against production hooks; see VAL-01 in
[the roadmap](../../next-step/todo.md) for the per-mechanism test files.
M15/M16 additionally require runtime/encoder checks, and M18 requires the actual
installed-host gate. Passing the bounded offline core suite alone is not proof
that those gates ran, nor evidence of complete live-model or cross-platform
VAL-02/03 acceptance. Any future TODO remains untested, not passed.

## Multi-scenario extension of the matrix

### Retrieval and evidence fidelity

- Small, 100K+ and multi-megabyte stores; answer near beginning, middle and end.
- Exact identifiers, Chinese punctuation, mixed-language text, emoji, long
  unbroken tokens and CRLF/LF offsets.
- Different questions over the same corpus select different evidence subsets.
- "Continue" and "that one" use bounded recent task context without replaying
  all tool data. User constraints such as "never write production" remain active.
- Numeric/negative/zero values, units, versions, timestamps, uncertainty and
  entity-to-value relationships survive projection.
- Comparison needs multiple sources; conflicting versions are surfaced rather
  than merged into one invented fact.
- Empty/no-match results are distinct from index unavailable, revision mismatch,
  permission denial, incomplete Top K and actual irrelevant candidates.
- Retrieved references remain untrusted; document text cannot override rules.

### Storage and lineage

- Failed/cancelled/interrupted responses retain independently completed tool
  results; failed operations remain distinguishable from successful ones.
- Streaming results are not published as final evidence.
- Fine chunks preserve parents, necessary headers and source ranges without
  duplicating the whole parent in every model request.
- Deterministic projection caches key source version and algorithm version;
  query-dependent selections also key the query/scope/policy.
- Legacy chats migrate lazily/idempotently; original evidence is unchanged.
- Multi-window writes, restart, partial publication, corrupt files, disk-full,
  source deletion/trash/restore and derived-index rebuild.
- Chat manifest size is bounded independently of referenced original context;
  large context is not duplicated into every receipt or feedback event.

### Providers and execution

- HTTP and native VS Code model adapters; actual tool schemas, images and
  countTokens conversion overhead; conservative fallback clearly identified.
- Budget exactly fits, one over, mandatory context alone over, tools alone over,
  unavailable/invalid tokenizer count and provider rejection.
- Ordinary send, retry, queue drain, steering and approved child delegation.
- Cancellation at retrieval/refinement/counting/persistence/send boundaries.
- Model/permission/account/root changes do not retarget an in-flight attempt.
- Read-only/untrusted/denied scope never gains access through refinement.
- Local resource caps are distinct from model window and response limits.

### Feedback and learning

- Strong user/verified feedback and weak model/action signals stay separate.
- Unselected candidates are not automatically negative labels; incomplete
  retrieval is not evidence of irrelevance.
- One episode links successive attempts; repeated event delivery is idempotent.
- Model/package, serving fallback, index generation and source versions are
  reproducible even after later changes.
- Collection disabled, opt-in, revoke, retention, delete and explicit export.
- No private corpus/query export in solution packages; no training on held-out
  test episodes; no automatic promotion of updated serving weights.

## E2E acceptance layers

1. **Controller/transport:** real disk store and loopback HTTP payload capture.
   Initial subset/evidence/budget regressions are executable in this baseline.
2. **Retrieval-worker integration:** real worker, corpus generations and selected
   solutions, final chunk materialization and actual serving attribution.
   Pending for the new context pipeline; existing worker tests are not a proxy.
3. **Extension Host/browser:** installed built artifact, History on, large
   synthetic history, UI trigger receipts, follow-up evidence retrieval, reload,
   cancel, retry and steering. Pending; use the existing host/browser harness.

Release acceptance requires no failing regressions, no remaining mandatory
mechanism TODOs, preservation tests passing, and measured payloads/receipts
agreeing. Do not claim host/worker E2E based on transport-only success.

## Recorded initial baseline

The initial build and the existing API Chat, retrieval-contract and
retrieval-snapshot suites pass. The new suite has 18 executable cases: 10 pass
and 8 fail, plus 18 explicitly unimplemented mechanism TODOs.

The executable failures identify:

- Recent tool evidence excluded from Chat Memory retrieval.
- Completed tool evidence lost in failed, cancelled and interrupted responses
  (three separate cases).
- Failed operation evidence excluded from memory.
- A changed source body retaining the same segment identity.
- Large history rejected by the 100,000-character guard before HTTP.
- Large history rejected by the selected 8,192-token budget before HTTP.

The transport controls pass for small input, empty knowledge results and
oversized pinned-context rejection. The baseline is intentionally red; TODOs
do not establish activation, compression or full E2E coverage.

## 3.2.16 baseline acceptance

The context suite has 44 cases: 26 executable passes, zero failures and 18
explicit future-mechanism TODOs. Existing API Chat and retrieval-contract
regressions also pass. New cases check:

- Exact/one-byte-over optional-context budgets, including tool schemas.
- Preservation of required input and live tool call/result pairing.
- Reproducible source ranges, outcome status and content-sensitive identities.
- Mixed malformed/valid provider output: rejection warnings and a healthy answer.
- A hung provider: five-second timeout, followed by primary model dispatch.
- Cancellation during a hung provider: prompt cancellation and no model dispatch.
- Post-budget receipts agreeing with actual loopback HTTP context.
- Oversized knowledge bodies omitted with an L2-required reason, never truncated.

The synthetic historical replay is 128,941 characters. The question about
docker-beta selects one 273-character tool-evidence reference, retaining the
exact metric, version and concurrency. The 8K-window transport regression sends
that evidence without unrelated tool output or disabling History, while leaving
original on-disk evidence unchanged. This is a synthetic acceptance measurement,
not a real-world retrieval quality benchmark.

The usable baseline does not claim complete replacement of Copilot's features.
Automatic structure-aware L2 refinement, learned Memory ranking, persistent
source blobs, training-feedback lineage and live installed-Host context E2E
remain explicitly unimplemented. Existing browser regressions exercise the Chat
UI and controller-backed persistence, not an installed-Host retrieval execution.
