# Tests

- Release theme matrix: after `npm run build`, run `node --test --test-concurrency=2 tests/test-chat-activity-browser.js tests/test-native-harness-browser.js tests/test-panel-instances-browser.js tests/test-native-harness.js`. The browser fixtures share four VS Code palettes from `ui-theme-fixtures.js`: dark, light, high-contrast and high-contrast-light. Checks include theme foreground pairing, native control color schemes, visible/unobstructed Send, settings containment, reachable Dashboard tabs and narrow Panel controls after explicitly collapsing its category sidebar. Set `PKM_RELEASE_UI_SCREENSHOT` to capture the Chat/Dashboard theme fixtures. These are deterministic rendering tests, not a full accessibility certification.

- Model settings readability: `node --test tests/test-chat-activity-browser.js tests/test-persona-profile-browser.js tests/test-persona-profile-ui.js tests/test-ui-build-artifacts.js` after a full build verifies long Profile-button text containment, checkbox sizing, labels not intersecting inputs, horizontal bounds at 1280/390/280px, and unchanged History message dispatch. Set `PKM_SETTINGS_SCREENSHOT` to capture those settings fixtures.

- Four-diagram Dashboard: `npm run test:chat-report-ui` covers the shared fixed 2 x 2 thumbnails, four detail tabs and thumbnail-to-tab selection, keyboard navigation, compact Harness arrows and evidence inspection, category-only retrieval blocks (no item hashes or labels), and desktop/narrow-window parity between Visualization and standalone Agent Sessions. `PKM_RING_SCREENSHOT` and `PKM_VIS_WINDOW_SCREENSHOT` optionally capture the deterministic browser fixtures.

- Automated JavaScript and Python regression tests live directly in this directory.
- Manual test matrices and behavioral cases live in `cases/`.
- Retrieval-first Chat context uses the [context test matrix](cases/CHAT_CONTEXT_TEST_CASES.md). Run `npm run test:chat-context` for executable context regressions and mechanism checks. The current core suite passes; real encoder, installed-host, live-model quality, and broader platform acceptance remain separate gates, not results inferred from offline fixtures.
- Run the real Extension Host startup smoke test with `npm run test:startup`. It uses VS Code 1.90.0, verifies activation, command registration, Panel creation, and the Webview ready handshake. The first run downloads the test instance; Linux hosts require `DISPLAY` or Xvfb.
- Run the full release gate with `npm run test:release`.
- Directly running every top-level test file is not a substitute for the release wrappers or their prerequisites. `test-recipe-browser-ui.py` requires a preview server; `node scripts/run-recipe-browser-ui-test.js` starts and cleans up its own isolated server. For `test-agent-snapshots-browser-ui.py`, start the synthetic release preview and pass `--url http://127.0.0.1:4178/?view=agentSnapshots` explicitly (its standalone default uses a different port). Retrieval serving/solution Python tests require a dependency-complete retrieval interpreter and the pinned engine; `resources/retrieval_runtime.py` exposes `activate_engine()` to verify and activate the bundled wheel before importing the tests. The real encoder feedback gate also requires `PKM_RETRIEVAL_TEST_PYTHON` and `PKM_RETRIEVAL_TEST_MODEL` pointing to existing offline resources. Missing prerequisites must be reported, not silently counted as successful tests.
- `npm run test:browser:full` includes Router learning, feature introduction, local Portal transport, and two-machine Git fixtures in addition to Chat, Recipe, and Extension Host startup. These local fixtures are not real GitHub ACL, paid-model, or cross-platform acceptance.
- `npm run test:retrieval-learning` verifies persisted HTTP-worker calibration and cutoff behavior, the rendered graphs and polling lifecycle, read-only observation, and generated FastMCP stdio feedback/limit contracts. It requires the existing Playwright/Chromium test environment and FastMCP Python dependencies; set `PYTHON` / `PKM_RETRIEVAL_TEST_PYTHON`, `PKM_PLAYWRIGHT_PATH`, and `PKM_CHROMIUM_EXECUTABLE` when using externally managed test tools.
- Source ownership and migration checks are described in [Source Ownership](../docs/source-layout.md). They run in postbuild and the UI artifact gate.
- Stored Memory observation: `npm run test:memory-engine` covers real Python/SQLite reads, provenance, scope rejection (including forged ID prefixes), persistence and unchanged LRU/change streams. After a full `npm run build`, run `node --test tests/test-chat-context-contracts.js tests/test-visualization-window.js tests/test-visualization-window-browser.js tests/test-native-harness-browser.js` for the scoped bridge, missing-database no-create behavior, original-source revision checks, actual-level pyramid, statement paging, sent-versus-prepared manifests, organization errors and narrow-window rendering. Visualization browser tests also cover immutable User/Agent Profile snapshots, exact-hash sent-round proof, absent Profile records, and empty retrieval-tail preservation. `python tests/test-chat-visualization-ui.py` verifies direct window entry without an inline panel, draft loss, model calls or cross-Chat targeting. These are deterministic local/browser tests, not a new semantic-quality or paid-model acceptance. The memory-engine command runs plain `tsc`; rebuild full bundles before packaged-host checks.
- Chat debugging follow-ups keep a bounded mandatory ledger of recent executed-tool identities instead of relying only on optional lexical recall. Context regressions also check the configured model/host boundary, History-off exclusion, no side-effect replay and the existing measured 8192-context eviction thresholds. These are deterministic contracts, not a claim that every live model will choose the right diagnostic command.
- The context/controller suites also exercise bounded HTTP and native VS Code debug completion, actual local log/process diagnostics, precise blocked outcomes, cross-process queue editing holds, active-request completion while editing, ordered single-request batches, and oversized-batch preservation. The activity browser suite verifies INFO-only tokenizer classification, hidden input/output counting rows, editor focus, restored drafts and rejected-save/cancel handling. Synthetic provider decisions verify wiring and safety, not live-model reasoning quality.
- `node --test tests/test-chat-diagnostic-logs.js tests/test-chat-context-contracts.js` checks scoped host-log discovery/read, traversal and symlink denial, bounded byte windows and literal filtering, common secret/payload redaction, and model discovery of current tool-call identities before recording debug evidence. Fixtures never read real credentials. Live Copilot acceptance is recorded separately; it exposed the hidden-log and opaque-call-ID gaps these tests now cover.
- `node --test tests/test-chat-work-goal.js tests/test-chat-context-contracts.js tests/test-chat-history-storage.js tests/test-chat-transport-receipts.js tests/test-api-chat.js` checks stable original objectives, all-input acceptance, evidence-linked outcomes, blocked-answer recovery, cancellation and host-recovery disarming, and explicit resume without effect replay. The HTTP controller fixture starts with one user delegation, rejects an early diagnostic-only ending, actually repairs a local fixture and runs a symptom check; the test independently rereads the result. The provider decisions are scripted: this proves end-to-end wiring, not uncoached real-model autonomy. The helper suite is also part of `npm run test:chat-context`.
- `npm run test:action-authoring` checks the discoverable Action schema, non-persisting preflight, field-level errors, isolated grant/qualification/call, real loopback HTTP boundaries, a real fake Azure CLI executable, typed status failures, durable monitoring/restart/deadline/cancel gates, event replay/retention gaps and generated MCP stdio transport. Select an existing Python environment with FastMCP/jsonschema on `PATH` and set `PYTHON` for the JavaScript transport tests if needed. This gate never queries Azure DevOps or resumes a production monitor.

Planning documents are kept separately under `docs/planning/`.
