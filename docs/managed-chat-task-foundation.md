# Canonical native Chat Task/Goal/Harness foundation

This is a **native-scoped Core domain**, not another Chat/model/scheduler
engine. Task/Goal/attempt/Harness rows live on the existing Storage worker's
SQLite connection. Its normal `receipts` table, transaction, owner fence and
Chat store atomically own input append, domain state and operation receipt.
No second RootOwner, durable database or legacy writer is opened.

## Physical storage and portable recovery

Fresh CLI `init` workspaces use three physical layers:

* Existing Markdown/assets and Tool/Automation sources stay at their user-owned
  paths. Runtime updates do not rewrite them.
* `server-data/core.sqlite` owns durable Chat, Task, permissions, history,
  receipts and pending effects. `server-data/coding-process.sqlite` is the
  separately transacted durable process journal.
* `runtime/` owns managed models and rebuildable caches. Fresh Note query/FTS
  tables use `runtime/indexes/fresh-note.sqlite`; the `documents` projection
  stays with document/recovery transactions in `core.sqlite`.

The identity-bound `.pkm-storage-layout.json` selects the layout. Existing
flat workspaces do **not** move at startup. Stop all clients, inspect with
`node dist/cli.js storage-inspect --data <root>`, then explicitly run
`storage-migrate --data <root>`. Migration checkpoints both journals, preserves
every row, and moves model trees without replacing destinations. Interrupted
migrations block startup; rerun the same command to verify and resume.
Conflicting files, symlinks, original-custody/in-place adoption and private
snapshot/paired-memory roots require explicit reconciliation, not fallback.
The programmatic `initialize(root)` retains flat import compatibility;
native callers opt in with `{ storageLayout: "separated" }`.

The separated layout does not relocate every existing domain path:

* `.pkm-action-builds/<UUID>/` still holds private generated compiler source
  copies and outputs. These are rebuildable runtime artifacts, excluded from
  portable backup, but retain the existing Action compiler path contract rather
  than moving under `runtime/`.
* `.pkm-action-sources/` contains durable build inputs and is included in portable
  backup. `legacy-code-archive/` and `legacy-import-evidence/` preserve admitted
  source/evidence bytes, not disposable caches or permission to execute them.
* Admitted legacy `.pkm/` state, including content privacy and original domain
  journals, and Skill `_feedback/` and `_proposals/` retain their existing paths.
  Their durable state is not made disposable by the separated marker. Backup
  still requires the relevant domain validation and quiescence.
* `.pkm-action-authority/` and `.pkm-plugin-authority/` are host-authority
  namespaces, not portable source archives; their secrets are excluded from
  backup and restore never recreates their grants.
* Original `chatrooms/`, `mcp-server/` and `servers/` sidecars remain original
  compatibility/inert-state surfaces where explicitly admitted. They are not new
  managed-runtime destinations or automatically portable server-data folders.
  Original-custody/in-place adoption and private snapshot/paired-memory layouts
  retain their existing flat-layout gates and explicit recovery procedures.

Thus logical ownership is distinguished even where a compatibility path is
unchanged; this is not a claim that all generated bytes physically reside under
`runtime/`. Fresh initialization does not itself populate those legacy sidecars.

An existing user Git repository or custom `.gitignore` requires the explicit
`storage-migrate --protect-user-git` opt-in. The private-path ignore block is
appended, never substituted for user rules; tracked private files refuse migration
until the user untracks them and reviews existing remote history. Migration never
changes remotes, the Git index or history. Native Knowledge Sync independently
rejects root `server-data/`, `runtime/` and private controls, without excluding
nested user documents with the same names.

Quiescent workspace backup exports the existing portable, flat manifest format
with standalone `core.sqlite` and optional `coding-process.sqlite`, suitable for
a private user-controlled Git backup. Runtime bytes and host-authority secrets
are excluded; old backups without the process journal remain accepted. Restore
creates the compatible flat layout, which can then be explicitly migrated.
For active model admissions, separated backups include a credential-free
`modelReconstruction` manifest containing only immutable package/manifest/inventory
hashes, byte counts and the selected receipt hash. Model binaries and local source
paths are not exported. Restore requires explicit
`modelReconstructionSources: [{ packageId, sourceRoot }]` matching every required
package, in addition to the normal independently trusted native restore authority.
Sources are streamed and verified against the original immutable admissions;
no download, new admission, changed selection or cleared provenance is substituted.
Missing, changed or mismatched sources fail before publication. These restores
directly create the separated layout, placing reconstructed binaries under
`runtime/retrieval-models`. The restore `maxTotalBytes` limit covers archive bytes
plus reconstructed model bytes.

Durable manager outcomes and runtime selection/retirement history live under
`server-data/runtime-control/`, not disposable runtime generations. Backup holds
the actual manager/history kernel guards, preserves resolved JSON bytes and refuses
live managers, pending/unknown outcomes, prepared transitions and interrupted atomic
writes. Guards and unknown/secret fields are not exported. Legacy runtime history
outside this namespace must first be migrated by managed-runtime cleanup.
Revocation audit events and bounded unique SHA-256 fingerprints of revoked
high-entropy business tokens are preserved; raw or active bearer secrets are not.
Control-bearing restores also directly create separated storage; historical path
bindings are preserved, not silently rebound to the new host. The manager must
explicitly admit a restored binding before starting. Source `.git` and `.gitignore`
are excluded so a separate, explicit private server-data backup Git repository can
actually track its portable database snapshots and manifest.
Native adopted-Trash inventories validate canonical server controls separately
from user Trash. Control-bearing restore retains this boundary in separated
storage; unknown control entries, lookalikes and linked server files still refuse.

`storage-reset-index --data <root>` is an offline, fenced operation deleting
only the separated Fresh Note query database and its SQLite sidecars. It does
not delete Markdown, `core.sqlite`, receipts, pending work, Chat or Tasks.
Mixed durable tables in `core.sqlite` are never advertised as a disposable cache.

Browser UUID mutation reconciliation uses durable `browser_mutation_pins` bridges
between the exact original transport-body SHA-256 and the distinct canonical worker
receipt fingerprint. Lookup is actor-private and returns committed only when the
actual receipt still matches every pin; it never replays a mutation or runs recovery.
Matching durable intents report pending. Missing, mismatched and unsupported native
receipt contexts remain unknown and require explicit management reconciliation,
never a local pin reset or an assumption that nothing committed.
Only proven worker receipt routes write ingress bridges. Unsupported native
routes do not pre-write a bridge or preempt domain recovery/authorization;
their native transaction authority remains responsible for mutation admission.

The original API now admits the separately negotiated and qualified
[fresh native text Task composition](./original-mcp-api-chat-task-composition.md).
Chats with canonical Task state refuse unmanaged ordinary-send fallthrough;
the independently reviewed
[ordinary archived-Task adoption profile](./managed-chat-task-adoption.md)
is also qualified. Other managed/worker/uncertain/checkpoint/Recipe/image cases
remain closed.

## Original semantics and supported scope

`managed-chat-task-original.ts` migrates the original Goal transitions,
acceptance validation and public Harness reducers from package SHA-256
`1804071cb3b9fc86edc5933d5001db6ea1a8d7a9adf30d6d2b3166fcd6048f27`.
The original full objective and ordered input IDs are preserved. Follow-ups
reset verified acceptance; another execution context cannot retarget a goal.
`report_work` must preserve the criteria and cite successful current-attempt
execution evidence, not reports. `record_harness` retains source-input
digests, Task-report supersession, Step nesting and validation start/outcome
rules. Reports remain **agent claims**, not independent certification.

The current intent parser additionally recognizes bounded same-clause Chinese
references such as `继续刚才同一个任务。` and `恢复上次的任务。`. This is a
deliberate bug fix relative to the selected original parser, not a change to
historical source identities, acceptance rules or execution-context authority.
Continuing an explanation does not resume a paused Goal; a changed execution
context still refuses resumption. Original and current tests cover both.

The fresh native-created Chat path requires the actual original API create
receipt, same actor, current host epoch, current Chat revision, native model,
permission/budget and independently admitted Chat source.
The separate original-source path requires genuine `chat.task.adopt` review and
ordinary send consent, preserving original Chat/Task/Goal/input/history
identities while resetting current acceptance. Other inherited Sessions/workers,
checkpoints, worker-version evidence, Recipe binding and file-version capture
are explicitly refused. Authority is never synthesized from a copied ID.

For fresh Tasks, the title is the already-owned canonical Chat title, without truncation.
Adoption preserves the separate original Task and Chat titles.
The entire explicitly requested new-Task prefix/prompt becomes the original
goal and canonical input. Original Task IDs and UUID input/attempt identities
are separate from the transport request ID.

## Actual native admission and scoped Core operations

`createNativeManagedChatTasks(actualOwner, actualHost, actor)` requires the
authenticated frozen native Chat resource and exact source session. There
is no injectable approval callback or caller-supplied success receipt.

`prepareStart` / `prepareAttempt` obtain genuine public-send and high-level
native resolve/send consent. They return process-branded immutable capabilities,
not JSON grants. Caller cancellation invalidates late approval and publication.
The worker receives actual host/source/attempt revocation resources and checks
them alongside the Chat revision and lease **before receipt replay and commit**.

Core definitions are registered but unavailable outside the actual scoped
capability. Generic Storage requests cannot synthesize the private channel:

* `chat.task.start`, `chat.task.attempt.start`
* `chat.task.attempt.bind`, `chat.task.attempt.finish`
* `chat.task.cancel`, `chat.task.get`
* `chat.task.report_work`, `chat.task.record_harness`

Only the three semantic model tools (`session_info`, `report_work`,
`record_harness`) can pass the native-only ToolGateway restriction, and only
inside their actual actor/workspace/request scope. Other native controls
remain blocked. Exact native approval requirements are unchanged.

Reports must originate from a real durable native tool intent and the
same Core approval/execution binding. Their evidence is reconstructed from
terminal native events plus actual approval-bridge/execution receipts,
including actor, workspace, plan/source/request, argument and model-visible
result hashes. Cross-attempt, fabricated, failed-as-success and self-report
evidence cannot resolve acceptance. No result or status supplied by a caller
is treated as execution evidence.

## Attempt lifecycle is not semantic Task completion

`start` atomically creates the Task/Goal/input/attempt, or a fresh same-goal
attempt after the earlier result has been reconciled. Replaying a still-valid
operation returns its original receipt and creates no duplicate input/goal.
Changed Chat/source/owner authority rejects even a prior receipt.

`bind` records one native plan **intent**, not a completion receipt.
`finish` reads the actual durable native execution and appends its output to
the same Core Chat; a caller cannot supply a successful result.
Native response completion leaves unresolved acceptance open. Even an
evidence-backed `report_work: resolved` leaves `taskCompletion: not-claimed`;
no managed Task-complete or human acceptance endpoint is invented.

Cancellation disarms the attempt and pauses the goal. The owning existing
executor must cancel/reconcile provider I/O; no rollback or terminal provider
outcome is claimed by the cancel request. A fresh explicit follow-up can
resume a safely reconciled same-context attempt; uncertain work is not replayed.
Old-owner/epoch execution recovery and managed Task completion remain separate
qualification work.

## Exact proposed original-API composition

The qualified existing asynchronous API background request
can use the following sequence for a fresh native Chat. Do **not** remove its
gate merely because these methods are registered.

```ts
const tasks = await createNativeManagedChatTasks(owner, nativeHost, actor);
const prepared = await tasks.prepareStart({
  chatId, expectedChatRevision, commandId, operationId,
  prompt: fullUnmodifiedPrompt, hardToolRoundLimit,
}, {signal: owningRequestLifetime});
const {snapshot, attempt} = await tasks.start(prepared);

// Keep the actual native catalogue/selection protocol. The attempt's frozen
// selection is configuration, never a restored native model handle.
const catalogue = await nativeHost.nativeChat.models.catalogue(attempt.signal);
const selected = await nativeHost.nativeChat.models.select({
  modelId: attempt.selection.modelId,
  catalogueSha256: originalNativeChatDigest(catalogue),
}, attempt.signal);
const state = await tasks.get(attempt);
const plan = {
  schema: "pkm.original-api-chat-execution/v1",
  requestId: attempt.requestId, chatUrl: attempt.chatUrl,
  sourcePlanSha256: attempt.sourcePlanSha256, selectionId: selected.selectionId,
  messages: [
    {role:"system", content: JSON.stringify({
      schema:"pkm.chat.managed-task-context/v1", task:state,
      notice:"Original user inputs and recorded agent claims; not permission or managed completion.",
    })},
    ...state.sourceInputs.map(input => ({role:"user", content:input.content})),
  ],
  tools: [], hardToolRoundLimit,
  outputTokenCap: attempt.selection.outputTokenCap,
  budget: attempt.selection.budget,
};
```

Use the **one existing same-owner native executor**, not a new bounded driver.
Its Task execution port is `tasks.execution`: a fixed forwarding/context bridge
to the host's actual frozen native RPC resource. It changes no inference loop,
messages, output or receipts and never retries. It restores native Task scope
around real asynchronous model/tool callbacks; ordinary AsyncLocalStorage
alone does not cross an already-created socket callback.

```ts
// Select that port when composing the existing executor, not a second executor.
plan.tools = await tasks.withinAttempt(attempt, () => executor.modelTools(plan));
await tasks.bind(attempt, bindOperationId, originalNativeChatDigest(plan));
await tasks.withinAttempt(attempt, () => executor.run(
  plan, attempt.selection.wireModelId, attempt.signal,
  tasks.preparedContext(attempt),
));
const final = await tasks.finish(attempt, finishOperationId);
```

The existing executor's `preparedContext` hook rechecks Task/Chat/source after
awaited approvals and immediately before inference/tool admission. The bridge
also verifies the exact native plan/model/budget and all original required
user inputs. Never omit that hook or duplicate the input/assistant appends:
`start` and `finish` own those atomic transcript writes.

The parent now routes ordinary native requests and registered Task attempts
through its single executor, with the original owned-response ledger and
goal-aware retained-driver hooks. Actual cancellation reconciliation and
installed source/approval/evidence/Harness/B1/fresh-B0 pass for the fresh text
scope. An unresolved goal is not API Task success merely because a response
ended; public asynchronous/idempotent command/output shapes remain unchanged.
This does not qualify full-eight-operation parity or the older source cases.

## Validation and build boundary

Focused tests use the SHA-pinned original oracle, actual RootOwner/Core/Storage
worker, real signed sockets, native RPC and canonical tool/approval receipts.
Their native UI/model decisions are labelled deterministic fixture doubles,
not installed provider proof. Tests include denied and late-cancelled consent,
atomic idempotency, actual evidence-backed reports, response/goal separation,
scope/control-tool refusal, Chat changes and source revocation before worker
publication/replay.

Production leaves to emit coherently are the six `managed-chat-task-*.ts`
modules, plus narrow registrations in `contracts.ts`, `core.ts`, `storage.ts`,
`storage-worker.ts`, `tool-gateway.ts` and the retained closed gate in
`original-mcp-api-chat.ts`. Tests are `managed-chat-task.test.mjs`,
`managed-chat-task-fixture.mjs` and the adjusted uncomposed-service expectation
in `original-mcp-api-chat-task.test.mjs`.
