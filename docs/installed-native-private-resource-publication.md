## Exact supported scope

Only existing **PUBLIC owner moves** with checked stored PRIVATE legacy
`_assets` references qualify. `update_note`/`update_paper` change title/category;
`update_skill` changes category. The original public signatures stay unchanged:
there is no grant, private-permission boolean, new file path or submitted
private Markdown in MCP arguments.

This is **not generic private publication or same-path content-update support**.
The subject validator requires distinct before/after paths. The current
canonical pipeline only plans legacy copies through relocation (`moveTo`);
same-path updates have no such publication plan. A later in-place increment
requires an explicit journaled lifecycle/intent/effect/recovery contract, not
merely removing that guard. The focused helper test checks same-path refusal.

Private owner/destination endpoints, arbitrary submitted private sources,
shared paired-tree ownership, malformed/unreviewed closures and general private
folder access remain closed. The separate native resource decision publishes
only its exact checked bytes to its exact public owned-pair destination for
this synthetic job. It does not unlock the file/folder or grant future access.
