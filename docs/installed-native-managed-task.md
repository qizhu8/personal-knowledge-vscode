# Installed native managed Task leaf

This disposable installed experiment uses a real registered `vscode.lm` provider,
the authenticated Task execution lane, the retained native stream, and the same
canonical owner/Core/executor. The provider is deliberately deterministic:
neither commercial-provider/keyring support nor human Task acceptance is claimed.
The helper is not an alternate Task engine and accepts no approval callback.

Parent actual-installed acceptance now passes on VSIX SHA-256
`8d8c75cdf3ff8c0df7cbc75cf970cf6f2538cb479b5dc50046e1d77acfc20e7d`,
payload `a99d5151280f7c26ab2432f1956ac737ea23a9336540818e22e6d7c20ba3310a`.
Use the separate cold scenario `--native-identity --cold-component --native-task
--legacy-vsix <original.vsix> --vsix <host.vsix>`. Actual native UI/provider,
canonical Goal/Harness/evidence, cancellation, stale captured approval, source
revocation, strict inventory and B1/fresh-B0 all passed; the private profile was
removed. The same candidate also passes ordinary installed native 31-round
model/Chat/Action-control regression. These are bounded fresh-native-text
results, not the held older managed/worker/checkpoint/Recipe/image paths.

provider registration, cold-component composition, coherent VSIX build, editor
exit, strict inventory, B1 retirement and disjoint B0 restore.

`pkm-native-managed-task-fixture`, model ID `managed-task-fixture`, label

The only base cold catalog binding is

bounded renderer observer; no shared cold UI/runner patch is included here.

## Actual business assertions

1. The ordinary original Chat cannot be promoted by an explicit new-Task prefix.
2. A real fresh native Chat is created with actual model choice, bind, create
   consent and read-only native presentation.
3. Denied exact send consent creates no Goal/input/attempt and calls no provider.
4. Two plain provider responses hit original stale-ending policy. The native
   journal is `failed`; the Goal is interrupted, never accepted or completed.
5. A separately approved follow-up retains the same Task/Goal/original objective
   and both ordered source inputs. Five genuine Core tools read the Note, record
   a Task report, start/complete validation, then report evidence-backed agent
   resolution. A sixth, tool-free hard-limit summary is the final response.
   The Task remains `active`, `taskCompletion: not-claimed`. Reusing the command
   does not invoke another model or duplicate canonical UUID transcript entries.
6. Another fresh Task enters an actual registered-provider wait. Genuine public
   cancel and native owned-cancel choices drive the actual VS Code LM cancellation
   token. No tools run; cancellation is not represented as rollback or acceptance.
7. A third fresh Task pauses at its actual first inference approval. A concurrent
   fixture operator appends a newer input using real canonical
   `chat.session.append` and its CAS/receipt transaction. This is explicitly a
   fixture operator mutation, not a model effect or fabricated approval.
   Only then does the renderer click the **same captured DOM node/button**.
   The stale request gets no authorized inference/provider call and cannot
   overwrite that newer input. Its unresolved binding requires reconciliation.
8. Independent genuine Chat-source revocation invalidates the actual source
   buffer while leaving the attachment/model catalog live. A subsequent API send
   is refused before publishing a command, Goal or effect.

Expected actual registered provider calls are **9**: two plain, six follow-up,
one cancelled. Denied/archive/stale/revoked phases must never reach it.
Expected canonical Task/attempt counts are **3 / 4**. These are assertions over
real runtime effects, not inventory counted as implementations.

## Renderer contract

`installedNativeManagedTaskUiStages` lists the 14 stages from
`native-managed-task-chat-source` through `native-managed-task-complete`.
The helper writes per-request and per-binding files from actual canonical state.
Those are observer expectations, never authority tokens or approval results.

The observer permits only normalized exact titles and expected structured
Root/workspace/profile/source/model/request/argument/plan identities:

- One source-only admission; original archive refusal.
- Three actual model Quick Picks / bind / create sequences.
- For each Task send: actual public submission, exact model selection, the
  Foundation's second genuine public consent, bind, exact send, actual Run limits.
  The denied send explicitly selects **Deny**.
- Every actual inference, Core record review and tool effect receives its own
  expected native modal choice. Generated write operation IDs must remain
  identical between review and effect approval.
- Replaying the successful command still receives its normal public-send
  confirmation, but no new binding, Task, input or inference. The replay has
  its own explicit renderer stage; idempotency is not permission inheritance.
- Actual owned cancellation, and a captured-node stale-approval handshake.

No Memory choice/HTTP fallback, worker/Recipe/checkpoint/file-version/image
composition, generic approve-anything loop or replacement modal is accepted.
This tests only fresh native-owned text Chats; it does not restore old managed
sessions or grant authority from copied descriptors.

## Preservation and validation status

Original Chat file inventory **and bytes** must remain unchanged, not merely
present. Restore verification checks actual retirement/B0/B1 manifest hashes,
disjoint root identity, archived SQLite integrity and exact canonical
Task/Goal/Harness/native execution/approval/receipt/transcript rows. Fresh B0 must
contain no native database/active marker; the original Root is not overwritten.
The verification result leaves B1/B0 flags false until the parent really performs
that lifecycle and calls the separate restoration verifier.

Focused validation: **4 helper/provider rule tests + 3 real Chromium/CDP/DOM
observer tests passed** in unchanged UID-preserving Linux isolation. API doubles
and the synthetic DOM in those tests are explicitly not installed/native
qualification. The separately identified parent installed run above supplies
positive and recovery proof. Its first observer failure waited on a lazily
created execution table too early; another omitted the replay's public modal.
Those were corrected in fixture observation only, without inventing state,
loosening a timeout or skipping an actual approval. The seven helper/DOM tests
also pass after that correction.
